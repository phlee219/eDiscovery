01 / OVERVIEW

다른 사람에게는 이렇게 설명하면 됩니다Product overview

In English

LEE is a local Windows tool for examining and editing eDiscovery load files. It compares records by exact document ID, updates metadata, runs production QC, and creates verified exports, delivery packages, and file manifests. It uses disk-based indexes for large load files and verifies generated output and the actual saved file.

LEE는 eDiscovery 로드파일을 로컬에서 읽고, 문서 ID 기준 비교·메타데이터 수정·납품 QC·새 파일 내보내기를 수행하는 Windows 도구입니다. 큰 파일 전체를 표로 메모리에 올리는 대신 원본 위치를 인덱싱하고, 처리 결과와 실제 저장된 파일을 검증합니다.

Relativity나 Nuix 자체를 대체하는 처리·리뷰 플랫폼은 아닙니다. 그 플랫폼에 올리기 전이나 납품 전에 로드파일과 관련 파일의 문제를 찾고, 지정한 변경을 수행하고, 근거가 남는 결과물을 만드는 도구로 설명하는 것이 정확합니다.

업무 관점

“Original과 Updated가 어디서 다른가?”, “누락된 native/text/image가 있는가?”, “특정 필드만 안전하게 바꿀 수 있는가?”, “고객에게 줄 파일을 올바르게 만들었는가?”에 답합니다.

개발 관점

파일 파서, 디스크 인덱스, 데이터 뷰, 작업 엔진, 검증·출력 엔진 위에 WinForms 화면을 얹은 구조입니다. 기능 대부분이 같은 데이터 접근 규약을 공유합니다.

왜 큰 파일에서도 동작하도록 설계했나요?

200만 행을 200만 개의 화면 행이나 큰 DataTable로 상시 보관하지 않습니다. 원본 파일은 그대로 두고, 행마다 어디에서 몇 바이트를 읽어야 하는지를 디스크 인덱스에 기록합니다. 그 행이 필요할 때 원본의 해당 위치를 읽습니다.

원본 파일:  [헤더][행 1][행 2] ... [행 2,000,000]
행 인덱스:  [행1 위치, 길이][행2 위치, 길이] ...  ← 디스크
화면 요청:  Row(1234) → 해당 위치 읽기 → 필드 배열 반환

DatWorkspace.OpenCore에서 인덱스 항목은 위치와 길이 두 개의 64비트 값입니다. 이것만 계산하면 행당 약 16바이트의 인덱스이며, 200만 행이면 약 32MB의 디스크 인덱스입니다. 원본·다른 인덱스·캐시 전체가 32MB라는 뜻은 아닙니다.

그리드는 VirtualMode=true이고 한 페이지에 1,000행을 표시합니다. GridPreviewCache는 화면용 축약값을 제한된 크기로 보관합니다. 화면에 보이는 축약값을 Export의 원본 데이터로 사용하면 안 됩니다.

필터와 정렬도 원본 파일을 다시 쓰지 않습니다

  • 필터 (Filtering): 표시할 원본 행 번호의 목록을 보관하는 RowMapView를 만듭니다.
  • 정렬 (External sorting): 묶음 단위로 키와 행 번호를 정렬해 디스크에 쓴 뒤 병합합니다. 결과 역시 “행 번호 순서표”입니다. 64비트 프로세스의 묶음은 최대 500,000개 키 또는 32Mi 문자입니다(4.0.3, DiskOperations.SortRunItems403). 32비트로 실행되면 예전 크기 5,000개 / 2Mi 문자를 씁니다.
  • ID 찾기/매칭 (Exact ID lookup / matching): ExactIndex가 정확한 문자열 ID를 찾습니다. 큰 항목은 디스크에 저장하고, 인덱스마다 최대 4 MiB의 페이지 캐시만 RAM에 둡니다(3.7.0). Go to ID(3.9.8)도 같은 인덱스를 캐시해 반복 이동 때 다시 만들지 않습니다.
  • 파싱 (Parsing): 한 번에 전체 파일을 문자열로 만들지 않고 스트림에서 레코드를 읽습니다. 인코딩·구조 오류는 무시하고 넘어가지 않습니다. 3.9.5부터 문자 하나씩 읽지 않고 디코딩한 블록을 직접 훑어 열기가 약 4.7배 빨라졌습니다. 규칙·오류 메시지·바이트 범위는 그대로입니다.
  • 해시 (Hashing): 전체 SHA-256은 HashPipe396의 별도 스레드에서 계산합니다(3.9.6). 파싱·쓰기와 동시에 진행할 뿐, 같은 바이트를 같은 순서로 해시하므로 결과는 같습니다.
  • 블록 읽기 (Block reads): 순차 스캔은 행 위치 인덱스를 4,096개씩(3.9.5), 필터·정렬 결과의 행 번호표를 8,192개씩(4.0.3) 묶어 읽습니다. 임의의 한 행으로 이동할 때는 여전히 그 항목만 읽습니다.
04 / DATA MODEL

master, view, DataSetView만 이해해도 절반은 읽힙니다Data views and edit history

In English

The master is the complete current working dataset; a view may contain filtered or reordered rows. Edits are represented through data views and disk-backed changes. Undo and Redo manage working state and its dependencies.

master · 전체 작업 데이터 / Complete working dataset

현재 작업 상태의 전체 데이터입니다. “원본 파일과 항상 동일한 값”이 아니라, 이미 승인해 적용한 변경이 포함될 수 있습니다.

view · 지금 보는 데이터 / Current view

전체 데이터이거나, 필터/정렬된 일부 데이터입니다. 화면의 선택한 셀, 현재 페이지, view, 전체 master는 서로 다른 범위입니다.

DataSetView는 데이터 접근 약속입니다

DataWorkbench.Apply는 기존 상태를 잡고, 작업 결과를 만들고, 잠긴 필드와 전체 레코드를 검증한 뒤 새 상태를 활성화합니다. 필터된 부분을 바꾸면 해당 변경을 전체 master로 다시 연결합니다.

서로 다른 세 단계 · Three levels of validation

  1. 설정/인식 (Setup / recognition): 샘플에서 형식·인코딩을 인식하고 필드를 선택했습니다. 전체 파일 검증 완료가 아닙니다.
  2. 생성물 검증 (Generated-output validation): 임시 출력의 구조와 모든 관련 값을 예상 결과와 비교했습니다. 실제 저장된 파일과 동일하다는 증거는 별도로 필요합니다.
  3. 저장본 검증 (Saved-file verification): 실제 저장된 파일 전체를 다시 읽고, 구조·내용·SHA-256을 검증했습니다. 해당 이름·형식·입력·설정·도구 버전에 묶인 audit를 남깁니다.

내보내기의 안전 장치 · Export safeguards

원본/작업 결과의 의존성 유지
  → 새 임시 파일에 스트리밍 작성 + SHA-256 계산
  → 임시 파일 전체를 읽어 값/구조 검증
  → 원본이 아직 같은지 확인
  → 기존 파일을 덮어쓰지 않고 새 목적지로 이동
  → 실제 저장본 전체 다시 읽기 + SHA-256 확인
  → 검증된 파일의 pin 유지 / 필요한 재해시
  → 정확한 결과에 audit 작성

특정 로컬 원본과 단순 범위 뷰에서는 원본 읽기를 줄이는 최적화가 있습니다. 검증한 임시 파일과 실제 저장본의 전체 해시가 같고, 원본의 변경 불가능한 pin이 계속 유지되는 조건에서 적용합니다. 저장본 재읽기를 건너뛰는 최적화가 아닙니다. 알 수 없는/변환된/잠글 수 없는 뷰는 같은 최적화를 무조건 적용하지 않습니다.

3.9.6부터는 view가 바뀔 수 없는 경우(변경 불가능한 원본 pin) Export가 원본을 두 번이 아니라 한 번 읽습니다. 쓴 값들의 digest(ValueDigest396: 값마다 길이와 UTF-16 code unit을 SHA-256에 넣음)를 만들고, 임시 출력을 다시 파싱한 값의 digest와 비교합니다. 다르면 예전의 레코드별 원본 비교로 위치를 찾아 “Saved output mismatch at record N, field F”로 거부하고 아무것도 게시하지 않습니다. 잠기지 않은/사용자 정의 view는 두 번의 원본 비교를 유지합니다. 3.9.7의 XLSX도 같은 조건에서 저장본을 다시 파싱하지 않고 해시로 확인합니다.

속도 최적화의 원칙: 같은 위험을 덮는 다른 증명이 있을 때만 중복 읽기를 줄입니다. “무결성 검사 건너뛰기” 옵션은 없습니다. 최적화가 들어간 경로는 대부분 스위치로 예전 경로와 A/B 비교해 출력 바이트가 같음을 확인했습니다.

개념쉬운 뜻주의점
SHA-256파일 전체 바이트의 지문같은 이름·크기·시간만으로 동일 파일이라고 판단하지 않습니다. 해시는 암호화나 사실 관계 검증이 아닙니다.
Source pin읽기 핸들을 잡아 로컬 원본의 쓰기/이동/삭제를 막는 상태로컬의 효과적인 잠금과 네트워크/비보장 잠금을 구분합니다. 비보장 상태는 재해시 등의 검증이 필요합니다.
Snapshot해당 작업이 사용한 입력·설정·범위의 고정된 조합나중에 입력이나 매핑이 바뀌면 예전 결과/승인을 새 작업에 적용하면 안 됩니다.
Provenance원본 경로·해시·변환/의존성의 출처 정보필드 이름만 같다고 같은 데이터/같은 업무 의도라고 볼 수 없습니다.
Audit도구 버전, 작업, 입력과 출력 해시 등을 적은 증거 파일결과 파일만 복사하고 audit를 잃으면 당시 검증 근거를 설명하기 어려워집니다.
고객에게 말할 수 있는 범위: “지정한 입력과 설정으로 만든 이 저장 파일의 자동 검증을 마쳤습니다.”
추가 확인이 필요한 범위: ticket/SOW의 업무 의미, 실제 redaction/content, 모든 companion의 완결성, chain of custody, Relativity/Nuix import 성공. 기능별로 무엇을 검사했는지 보고서와 audit에서 확인합니다.

관련 파일: IndexingWatch → DatWorkspace.OpenCore / IdComparison의 인덱싱 → OperationWindow.

검사할 순서: 실제 파일/경로 접근 → 선택 인코딩·BOM → 구분자/qualifier → 물리 파일 읽기나 디스크 캐시 접근 → 해당 단계에 watch가 적용되는지. 물리 rename/export 거래를 강제로 종료하는 용도로 IndexingWatch를 사용하면 안 됩니다.

사례 C · CSV가 Excel의 A열 하나로 들어감CSV delimiter / Single-column import

In English

Use the short English answers below as starting points for explaining the tool. Keep each answer within the checks actually performed for that job.

Q. 원본 DAT를 직접 고치나요?Q. Does LEE modify the original DAT?

기본 메타데이터 편집은 작업 뷰를 바꾸며, Export는 새 파일을 만듭니다. 원본 DAT를 덮어쓰는 방식이 아닙니다. 예외는 사용자가 직접 고르는 File → Save(Ctrl+S)로, 이전 파일을 %LOCALAPPDATA%\LEE\SaveBackups로 옮긴 뒤 검증된 파일을 같은 이름으로 둡니다. 승인한 물리 rename/copy 작업도 native 파일에 별도의 영향을 줄 수 있으므로 구분해야 합니다.

In English: Metadata edits update the working view, and export creates a new file. Save (Ctrl+S) is the explicit exception: it moves the previous file to a backup folder and puts the verified file under the original name. Approved physical rename or copy operations are separate and can affect native files.

Q. 데이터가 다 메모리에 들어가나요?Q. Does LEE load everything into memory?

주요 로드파일 경로는 원본 + 디스크 행 인덱스 + 제한된 버퍼/캐시로 처리합니다. 매칭/정렬/변경값에도 디스크 기반 구조를 씁니다. 3.7.8부터 64비트로 실행되어 정렬 묶음 같은 버퍼를 키웠지만, 파일 전체를 RAM에 올리는 방식으로 바뀐 것은 아닙니다. 어떤 작업도 RAM을 쓰지 않는다는 뜻은 아니고, 모든 기능/입력 크기가 무제한이라는 뜻도 아닙니다.

In English: The main load-file workflows use streaming reads, disk-based indexes, and bounded buffers and caches. This reduces memory use; it does not make every operation or input size unlimited.

Q. 화면의 값이 잘려 보이는데 Export도 잘리나요?Q. Are truncated preview values also truncated in the export?

화면용 preview와 실제 값은 분리되어 있습니다. 현재 GridPreviewCache는 값당 512자 preview, 최대64행·약2Mi문자 캐시를 사용합니다. 전체 값은 편집/복사/처리/출력 경로로 읽습니다. 반대로 XLSX 등 출력 형식의 한계는 화면 축약과 별개이며, 한계 초과 시 중단하도록 되어 있습니다.

In English: The grid preview is separate from the full values used for processing and export. Output format limits are checked separately; exceeding a supported limit must stop the export rather than silently truncate values.

Q. Filter에서 100행만 보이면 QC/Export도 100행인가요?Q. Does a filtered view define the QC or export scope?

기능마다 scope를 확인해야 합니다. view는 필터/정렬 결과이고, master는 전체입니다. Package QC는 전체 데이터 기준입니다. Export에는 Complete dataset/current view 선택이 있습니다. 선택한 셀이나 현재1,000행 페이지가 전체 처리 범위를 뜻하지 않습니다.

In English: Check the operation scope. Package QC uses the complete dataset, while export lets you choose the complete dataset or current view. The current page or cell selection is not automatically the processing scope.

Q. ID의 앞자리 0이나 한글이 바뀌지 않나요?Q. Are leading zeroes and non-Latin characters preserved?

ID/필드 값은 기본적으로 문자열로 다룹니다. 숫자화, trim, Unicode 정규화를 자동으로 해 매칭하지 않습니다. 한글 보존에는 실제 입력 인코딩과 출력 인코딩이 맞아야 합니다. XLSX는 텍스트 셀을 사용하며 legacy CSV 손실은 별도 승인/증거로 구분합니다.

In English: IDs and field values are treated as strings. Matching does not automatically trim, convert numbers, or normalize Unicode. Character preservation also depends on correct decoding and an output encoding that can represent the values.

Q. QC가 오류 0이면 바로 납품해도 되나요?Q. Does zero QC errors mean the delivery is ready?

설정한 검사에서 오류가 없었다는 뜻으로 설명합니다. REVIEW와 NOT CHECKED, SOW, source/output identity, 실제 저장 파일, 별도 플랫폼 import를 확인해야 합니다. Quick 결과를 Full 해시 검사 완료라고 말하지 않습니다.

In English: It means no errors were found by the configured checks. Review the REVIEW and NOT CHECKED items, delivery requirements, saved-file evidence, and any required target-platform import checks.

Q. 해시가 같으면 모든 내용이 정확하다는 뜻인가요?Q. Does a matching hash prove the content is correct?

비교한 두 파일의 바이트 동일성을 확인하는 증거입니다. 예상 변환과 값 비교도 필요하고, 입력 자체가 올바른 고객/올바른 baseline인지의 업무 판단은 별도입니다. SHA-256은 암호화나 전자서명도 아닙니다.

In English: A matching SHA-256 supports byte identity between the compared files. It does not prove that the input is the correct baseline or that the requested business transformation is correct. It is neither encryption nor a digital signature.

Q. 설정을 기억하는데 왜 어떤 때 다시 고르게 하나요?Q. Why do remembered fields sometimes need to be selected again?

헤더 구조와 정확한 필드명이 현재 입력에 유효할 때만 재사용해야 하기 때문입니다. 과거 파일의 선택을 이름만 비슷한 새 파일에 강제로 적용하면 잘못된 매핑이 됩니다. 입력 경로·scope·승인·PASS를 마음대로 복원하는 것과 구분합니다.

In English: A remembered selection can be reused only when it is valid for the current header layout and exact field names. Similar-looking names do not establish a correct mapping.

Q. OPT를 합치면 이미지도 합쳐지나요?Q. Does combining OPT files combine the images?

OPT의 페이지 행을 합치는 것입니다. 실제 TIFF/PDF를 합치거나 이미지 경로를 다시 배치하는 작업이 아닙니다. 상대경로는 그대로 남으므로 delivery root와 실제 이미지 위치를 별도로 확인해야 합니다.

In English: No. It combines OPT page records. It does not merge TIFF or PDF content or relocate image files. Check relative paths and the delivery root separately.

Q. PAGECOUNT는 실제 이미지 페이지 수인가요?Q. Does PAGECOUNT reflect the actual number of image pages?

Bates Beg/End로 계산하는 기능과 OPT의 문서별 페이지 행을 세는 기능이 모두 있습니다. 전자는 메타데이터 범위, 후자는 검증한 OPT의 Y 경계·정확한 첫 페이지 ID가 기준입니다. 어느 쪽도 TIFF/PDF 내부 페이지를 전부 디코딩한 수라고 설명하면 안 됩니다.

In English: LEE supports both Bates-derived counts and OPT-derived counts. The former uses metadata ranges; the latter counts OPT page records after exact first-page matching. Neither decodes every page inside TIFF or PDF files.

Q. XLSX를 쓰면 Excel 설치가 필요한가요?Q. Does XLSX export require Microsoft Excel?

현재 핵심 XLSX 출력 엔진은 ZIP/XML을 직접 만듭니다. 파일 생성 때문에 Excel 자동화를 요구하지 않습니다. 파일을 실제 Excel/CX 양식/대상 시스템에서 잘 사용하는지는 별도 확인입니다.

In English: The core exporter writes XLSX ZIP and XML structures directly, without automating Excel. Actual use in Excel, a CX report template, or another target system still needs its own check.

Q. 세션 저장과 Export는 무엇이 다른가요?Q. What is the difference between saving a session and exporting?

Export는 고객에게 전달할 DAT/CSV/XLSX 같은 결과 파일입니다. 세션/복구는 현재 작업 데이터·뷰·이력·의존성을 이어가기 위한 상태입니다. 모든 임의의 데이터 뷰가 세션에서 지원되는 것은 아니며, 원본 경로/해시가 달라지면 복원이 차단될 수 있습니다.

In English: Export creates a delivery file such as DAT, CSV, or XLSX. A session preserves supported working data, views, history, and dependencies for continuation; it can be blocked if source paths or hashes change.

Q. 왜 “원본이 바뀌었다”는 오류로 멈추나요?Q. Why does the job stop when the source changes?

계산·검토했던 데이터와 다른 바이트로 결과를 만들거나 승인하면 잘못된 provenance가 됩니다. 이 경우 중단은 의도된 보호입니다. 실제 파일을 확인하고 올바른 입력으로 다시 시작해야 합니다.

In English: The result and approval must refer to the same source bytes that were processed and reviewed. A source change invalidates that basis. Confirm the correct source and restart with it.

Q. 내부에 299/305/316이 붙은 파일은 구버전인가요?Q. Do version numbers in source filenames mean those files are obsolete?

기능을 추가한 버전을 기억하는 이름인 경우가 많습니다. 현재 프로젝트에 포함되고 현재 handler가 호출하면 현행 코드입니다. public 배포 버전은 AssemblyInfo/WorkspaceEngine와 검증된 실행 파일, release 기록으로 판단합니다.

In English: Not necessarily. Many filenames record when a feature was introduced. If the current project includes the file and the current handler calls it, it may still be active code. Confirm the shipped version from the tested artifact and release evidence.

Q. 매니페스트가 모두 일치하면 납품 전체가 승인된 건가요?Q. Does a matching manifest mean the delivery is fully approved?

기준 매니페스트에 기록된 파일과 대조했다는 뜻입니다. 잘못된 기준 폴더로 만든 매니페스트도 그 폴더와는 일치할 수 있습니다. 고객/SOW 기준의 완결성·업무 의미·대상 시스템 import는 별도 확인합니다. 3.3.3에서는 OK 행 저장을 선택하고 audit의 manifest SHA-256으로 기준 목록을 식별할 수 있습니다.

In English: A match establishes the file comparison against that manifest. It does not prove that the manifest represents the correct complete production or that a target-platform import will succeed. The report audit identifies the exact manifest hash.

Q. QC 재개는 검사를 생략해도 안전하다는 뜻인가요?Q. What does RESUMED mean in Package QC?

같은 root·읽기 설정 아래 파일 ID·크기·수정 시각과 모드가 일치한 파일 결과를 이전 중단 실행에서 재사용했다는 뜻입니다. 보고서는 현재 데이터로 재구성합니다. RESUMED를 이번 실행의 새 파일 해시 검사라고 말하지 않으며, 새로 읽기가 필요한 업무라면 재사용하지 않고 시작하는 선택을 합니다.

In English: RESUMED identifies a file-level result reused from an interrupted run under the eligibility checks. It is not a fresh read or hash in the current run. The report is rebuilt from the current dataset; start without reuse when the job requires fresh reads.

Q. QC 보고서 비교와 DAT 비교는 같은 건가요?Q. Is QC-report comparison the same as DAT comparison?

DAT 비교는 문서 ID로 메타데이터를 대응합니다. QC 보고서 비교는 사용자가 선택한 구별 필드로 문제를 대응해 NEW/STILL PRESENT/RESOLVED를 보여줍니다. 3.3.3에서는 Tools 메뉴와 QC 결과 바로가기 모두 같은 구별 필드 선택과 기억을 사용합니다.

In English: DAT comparison matches document metadata by exact ID. QC-report comparison matches issue rows using chosen identifying fields and occurrence counts, then reports NEW, STILL PRESENT, or RESOLVED issues.

Q. CSV를 50만 건으로 나누면 aiR에서 반드시 열리나요?Q. Is 500,000 records a guaranteed aiR limit?

50만 건은 사용자가 실제로 열어본 경험을 반영한 시작점입니다. 레코드 길이·파일 바이트·필드 수·처리 환경과 대상 플랫폼에 따라 달라집니다. 가족 유지를 선택하면 part는 지정 건수를 넘을 수 있습니다. 실제 part 건수·바이트와 대상 환경에서의 결과를 확인합니다.

In English: No. It is a user-observed starting point, not a universal platform limit. Record size, fields, environment, and family-preserving splits affect the actual parts. Validate the produced files in the real target workflow.

Q. 서명된 EXE면 회사 보안 검사를 통과한다는 뜻인가요?Q. Does the signature mean the EXE is trusted?

자체 서명 인증서로 서명했습니다. 받은 파일의 바이트가 배포한 파일과 같은지 확인하는 데 쓸 수 있지만, 공인 CA가 확인한 게시자라는 뜻은 아닙니다. 회사 보안 제품의 판정은 별도입니다. .html로 받은 파일은 확장자를 .exe로 바꿔 실행하는 같은 바이트입니다.

In English: It is signed with a self-signed certificate. The signature can confirm that the bytes match the published file; it is not a publisher identity verified by a public certificate authority, and it does not decide how company security tools treat the file.

Q. 경로가 260자를 넘는 자료는 어떻게 하나요?Q. What about paths longer than 260 characters?

회사 PC는 Windows long-path 정책이 꺼져 있어 일반 경로로는 열 수 없는 파일이 생깁니다. File tree는 긴 경로도 목록에 포함하고(4.0.0), Copy folder with shorter names는 \\?\ 경로로 읽어 원본을 건드리지 않고 짧은 이름의 사본과 이름 대응표·Relativity용 로드파일을 만듭니다. 그 밖의 기능에서 260자 초과 경로는 수용한 한계입니다.

In English: File tree lists long paths, and Copy folder with shorter names reads them through \\?\ paths and writes a verified copy with shortened names, a name map, and a load file. The originals are not changed. Elsewhere, paths over 260 characters without the Windows long-path policy remain an accepted limit.

Q. 한국어 메뉴를 켜면 결과 파일도 한국어가 되나요?Q. Do Korean menus change the output?

아닙니다. 메뉴·툴바·우클릭 메뉴의 이름만 바뀌는 표시 설정입니다. 명령·단축키·대화상자·필드명·보고서·데이터는 같습니다. 툴팁과 Find command, Help에는 영어 명령 이름이 남습니다.

In English: No. Korean menus change only the labels of the main menu, toolbar, and context menus. Commands, shortcuts, dialogs, field names, reports, and data are unchanged.

변경 원칙

우선순위는 편의성·직관성·입력 최소화·실수 예방, 데이터 완결성을 유지한 속도입니다. 확인된 데이터 무결성 결함은 항상 먼저 고칩니다. 이름 힌트를 권한 있는 매핑으로 바꾸거나, 검증을 지워서 속도를 높이면 안 됩니다. 큰 개선은 최소 3개, 자잘한 개선만으로 구성한 배치는 최소 5개를 묶어 한 버전으로 배포합니다. 상한은 없지만 실패를 항목 하나로 좁힐 수 있게 추적 가능해야 합니다. 사용자가 요청한 항목은 따로 곧바로 만들어 배포합니다. 대화상자는 Full HD(1920×1080, 125% 배율 포함)에 맞춥니다.

테스트는 어디에 있나요?

workbench-tests(LEE.WorkbenchTests)는 커스텀 C# 실행 파일 기반이며 실제 WinForms 화면 테스트와 core/상태/무결성 테스트가 함께 있습니다. --v405-only처럼 모드를 골라 관련 테스트만 실행하고, 전체 suite(약 1,250개, 약 25분, 30분 제한)는 공용 엔진·플랫폼처럼 넓은 변경에서만 한 번 실행합니다. tests의 Export 실행 파일은 출력 엔진을 검사하고, tests/torture/는 인코딩·qualifier·깨진 행·1,000/1,001필드 등 합성 경계 사례를 독립 Python 판독기로 교차 확인합니다. Python의 독립 검사에서는 제품 파서/serializer를 그대로 재사용하지 않도록 설계합니다.

# C:\Coding\Tools\lee 에서 (PowerShell)
.\work\run.ps1 -Mode --v405-only -Name v405            # 한 번 빌드하고 모드 하나 실행, 실패와 요약 출력
.\work\run.ps1 -Mode --v405-only -Name v405b -NoBuild  # 다시 빌드하지 않고 재실행
# 결과: work\results\<Name>\results.txt

테스트의 passed=N은 해당 harness의 테스트 그룹 수입니다. “모든 고객 시나리오”나 “단언문 N개”라고 번역하지 않습니다. ForTests로 끝나는 hook은 변조/취소 같은 상황을 만들기 위한 도구이며, 제품의 검증을 무력화하는 해결책으로 쓰면 안 됩니다.

배포 구조

개발 폴더와 공개 배포 체크아웃은 분리되어 있습니다. 모든 빌드는 난독화하지 않고 서명해 배포하며, LEE.exe와 동일 바이트 LEE.html만 게시합니다. 소스·테스트·설정·고객 자료는 공개하지 않습니다. 사용자는 Git에서 내려받아 회사 네트워크로 직접 복사합니다.

현재 배포 절차(사용자 지침 2026-10-22/23):

  1. 변경마다 관련 집중 테스트를 통과시킵니다. 전체 suite는 넓은 변경에서만 한 번 실행합니다.
  2. 빌드한 뒤 테스트한 EXE에 서명합니다: Set-AuthenticodeSignature, 사용자 인증서 Cert:\CurrentUser\My\1FD12C…, SHA-256, timestamp 서버 없음. 서명 뒤 재테스트는 하지 않습니다.
  3. OLD\LEE_<version>.exe(+ .exe.config)로 백업하고(기존 백업은 절대 덮어쓰지 않음), root LEE.exe/LEE.html을 같은 바이트로 바꿉니다. LEE.exe.config는 로컬에만 둡니다.
  4. github-eDiscovery(remote phlee219/eDiscovery)에 두 파일만 커밋·푸시하고, 원격 바이트가 root SHA-256과 같은지 확인합니다.
  5. docs/lee-<version>-release-<date>.md를 쓰고 lee-version-history.md에 한 줄을 더하고 체크포인트를 갱신합니다.

예전의 동결(frozen) 캠페인, release receipt, 독립 reference 캠페인, native 이미지 검토, 항목별 불변 스냅샷, “동결 검증 2회 실패 시 중단” 규칙은 더 이상 쓰지 않습니다. docs/history/의 3.6.x–3.7.x 기록에 나오는 이런 단계는 당시 절차입니다.
